# 31.01 Grimoire Wiki-RAG and Hermes Boundary

## What changed

The Grimoire repository was bootstrapped with its own `wiki/` and documented
as the home for the standalone `grimoire-mcp` wiki-RAG service. The setup uses a
configurable `WIKI_RAG_PROJECTS_ROOT`, a disposable `WIKI_RAG_HOME`, and a
separate user-level 12-hour index refresh.

## Why

The goal is to make existing project documentation searchable across projects
without placing source text in Hermes configuration or exposing it remotely.
The refresh rebuilds derived BM25 indexes; it does not author or rewrite
Markdown.

## Compatibility correction

The Grimoire server source uses the MCP 1.x decorator API on
`mcp.server.Server`. The package therefore declares `mcp>=1.0,<2`, and
`grimoire-mcp/uv.lock` records the verified `mcp==1.29.0` resolution. The
regression test `grimoire-mcp/tests/test_mcp_compatibility.py` checks the two
decorator methods required by the server. This keeps a future dependency
refresh from silently selecting MCP 2.x, whose low-level callback API is not
compatible with the current source.

## Verify

```bash
scripts/refresh-wiki-rag.sh
find "${WIKI_RAG_HOME:-$HOME/.wiki-rag}/indexes" -name index.json -print
systemctl --user list-timers grimoire-wiki-rag-refresh.timer
```

Hermes was surveyed read-only and currently reports no configured MCP servers.
The optional `hermes mcp add grimoire-mcp ...` command is documented but was
not executed.

The current checkout refresh produced one project, three indexed files, and
three chunks. A bounded search for `Hermes wiki-RAG refresh` returned this note,
confirming that the derived index is queryable.

## Rollback

Run `scripts/disable-wiki-rag-timer.sh --remove-files`, remove the derived
`$HOME/.wiki-rag` directory and the ignored `config/wiki-rag.env` if desired.
Preserve the checkout, source wikis, and all Hermes files.
