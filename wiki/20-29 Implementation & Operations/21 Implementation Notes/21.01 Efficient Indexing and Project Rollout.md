# 21.01 Efficient Indexing and Project Rollout

## Design and scope — 2026-09-08

Implement the approved efficiency review: persist prepared BM25 data, reuse a
bounded per-project retriever cache, skip unchanged source sets, publish complete
index generations atomically, and run synchronous MCP operations in bounded
workers. Default project listing uses indexed counts with timestamps; callers
can request a live scan.

Roll out the wiki contract to all direct-child projects in the configured
projects folder. Preserve existing documentation and agent instructions. Install
a local runtime, register the stdio server with Codex, and configure the existing
midnight/noon refresh service. No source commits or deployments are involved.

## Verification plan

- Regression tests: persisted queries, cache invalidation, source additions and
  deletions, empty corpora, atomic publication, worker cancellation, cheap listing.
- Temporary 100-document benchmark: initial build, unchanged refresh, cold/warm
  query latency, peak resident memory. Compare identical runtime dependencies.
- Rollout dry run, apply, then a second dry run proving idempotence.
- Real stdio MCP calls: list all projects and search each wiki.
- Refresh twice and verify unchanged projects are skipped; inspect timer state.

## Rollback

Disable the named Grimoire refresh timer and remove only its units if desired.
Remove the named Codex MCP registration. Source wikis are durable; preserve any
subsequent user edits. Derived indexes can be rebuilt. Reverting implementation
requires rebuilding legacy indexes because the persistence format changes.

## Verified outcome

- Implemented prepared immutable BM25 generations and bounded retriever reuse.
  Cache admission is limited to eight projects / 64 MiB of persisted data; actual
  Python heap use may be larger. POSIX locks support the Linux/macOS runtime.
- Content hashes detect changes even when file size/mtime remain unchanged.
  Unchanged refreshes still read source bytes, but skip rebuilding and writing.
- Four worker slots retain capacity through cancellation. Listing uses compact
  metadata unless `live_scan` is requested; discovery refreshes on list/reindex.
- `scripts/setup-projects.py` previews by default, preserves existing files, and
  supports explicit project scopes. All five current projects were adopted;
  repeat preview reports zero writes. Existing Scout instructions were unchanged.
- Locked-runtime regression suite: **30 passed** using
  `grimoire-mcp/.venv/bin/python -m pytest grimoire-mcp/tests tests -q`.
  Tests include cross-process refresh, failed publication, cache budgets, removed
  sources, worker cancellation and rollout preservation. Async tests required
  execution outside the tool sandbox for local thread wakeup sockets.
- Actual stdio MCP initialization, tool discovery, listing and queries succeeded
  for all five projects. A repeat MCP refresh returned unchanged for all five.
- Codex registration `grimoire-mcp` uses the project-local runtime. The user-level
  refresh timer is active for local midnight and noon. Client reload is needed
  to discover the newly registered tools in an already-open session.

### Synthetic benchmark

Same locked Python 3.12 environment; 100 documents, six queries with the last
five used for the warm median. Baseline source came from Git HEAD before edits.
Use `grimoire-mcp/benchmarks/benchmark_indexer.py` to reproduce the workload.
These are individual local runs, not production latency guarantees.

| Measurement | Before | After |
|---|---:|---:|
| Initial build | 143 ms | 98 ms |
| Unchanged refresh | 34.2 ms | 2.61 ms |
| Cold query | 48.7 ms | 1.95 ms |
| Warm query median | 43.2 ms | 0.43 ms |
| Process peak RSS | 149 MiB | 144 MiB |

The measured gain comes from removing repeated chunking/BM25 construction.
Initial-build and RSS differences can vary between runs; no speedup is promised
for initial builds, which now persist additional prepared data.

## Automatic adoption — 2026-09-08

Enabled `WIKI_RAG_AUTO_SETUP=1` in the ignored local configuration. The existing
midnight/noon refresh now runs the idempotent setup script before indexing.
Every eligible direct-child project directory gains missing wiki template files,
agent guidance, a numbered adoption note and a session-log entry. Existing files
and documentation gates are preserved; hidden/generated/symlink projects are
skipped. New project scopes start with an explicit undocumented placeholder;
working agents fill in real project knowledge. This does not infer architecture
or author implementation notes from source code.

The option defaults to 0 for other installations. Dry-run mode prints both
commands without creating wikis or indexes. Disable automatic adoption by setting
`WIKI_RAG_AUTO_SETUP=0`; regular index refresh continues. Previously created wiki
files remain intact. No timer schedule or Codex registration change is required.

Verification: refresh-entry-point tests exercise setup-before-index order,
preservation and idempotence, disabled mode, and dry-run non-mutation. All eight
setup/refresh tests pass. New projects are picked up on the next scheduled sweep,
or immediately by running `scripts/refresh-wiki-rag.sh`.

The real service test exposed a long-note failure in NLTK's import guard: it
rejected the installed `regex` dependency because the virtual environment lives
beneath the working directory. Python safe-path mode did not resolve that guard's
ancestor-directory check. Chunking now uses explicit punctuation/whitespace
sentence boundaries, avoiding the lazy NLTK import and data download entirely.
Paragraph splitting, token budgets and overlap remain managed by SentenceSplitter.
The boundary setting is fingerprinted, so existing indexes rebuild once. A
long-note regression confirms the final chunk remains searchable without NLTK.

Final verification: **34 regression tests passed**. A disposable new project went
through the real refresh command, gained its wiki/AGENTS files, became searchable,
and retained the same index generation on a second run. The installed user service
then completed with `Result=success`, `ExecMainStatus=0`; its timer remains active.

## Proposed modernization — 2026-09-25

The [modernization specification](../../../docs/superpowers/specs/2026-09-25-grimoire-modernization-spec.md)
proposes a shorter mandatory wiki contract, documentation ownership for coordinating
agents, and bounded passage retrieval. The purpose is to decrease repeated context
without losing project knowledge between harnesses. The specification includes
upgrade and acceptance criteria. User approval is pending; no implementation or
project upgrades occurred. This documentation change needs no runtime rollback.
